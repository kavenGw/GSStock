# 趋势缓存写入锁冲突处理

`watch_alert` 在计算 TD 前调用 `get_trend_data()`，可能全量或增量获取历史行情并写入 `unified_stock_cache`。此路径并非全程只读缓存；缓存写入错误原先会中断后续告警判断。

`UnifiedStockCache.set_cached_data()` 遇到 SQLite BUSY / LOCKED 时，先回滚事务，再重新执行查询和写入。首次尝试失败后最多重试 3 次，退避为 0.2、0.4、0.8 秒。等待发生在回滚之后；数据库驱动自身的锁等待时间另计，因此 1.4 秒不是总超时上限。更新、新增及新增唯一键冲突后的更新均由同一层重试覆盖。

全量与增量趋势获取通过 `_save_trend_cache()` 保存缓存。锁重试耗尽时记录股票代码和缓存类型，继续返回已获取的数据并更新内存缓存，让本轮 TD 和告警判断继续。其他数据库错误仍抛出，非趋势缓存调用者也仍收到重试耗尽的异常。

此改动沿用现有共享 session 的提交边界，失败回滚同样作用于该 session；调用方不应夹带尚未提交的业务修改。没有更改数据库结构、服务器 journal mode 或驱动超时，也不能消除其他写入者长期占锁。服务器持锁者仍需结合现场日志确认。

部署更新后需重启运行调度器的进程。观察“缓存写入锁冲突”和“趋势缓存写入重试耗尽”日志；若持续发生，应排查长事务及并发写入任务。

回归测试使用临时 SQLite 文件及独立连接持有写锁，不访问业务数据库：

```sh
python -m pytest tests/services/test_cache_lock_retry.py -q
```

覆盖新增/更新锁释放后成功、重试耗尽后的 session 可用性、非锁错误不重试不吞掉、真实增量趋势路径保留新行情。
